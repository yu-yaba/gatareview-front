# 授業詳細の表示速度

Issue: https://github.com/yu-yaba/gatareview-front/issues/106

## 調査で分かったこと

以前の測定はGooglebotとしてHTML全体を取得する時間を見ており、通常のブラウザで最初の内容が描画される時刻（FCP）や主な内容が描画される時刻（LCP）は測っていなかった。取得時間と表示時間を区別する。

通常のChromeでブラウザキャッシュとService Workerを無効にして測定すると、受信開始よりも授業情報・レビューが表示されるまでの待ち時間が大きかった。従来の実装では、公開授業情報、セッション、レビューを順に取得し、レビューが返るまで授業カードも返さなかった。

Vercelの実行地域は東京のhnd1、HerokuのAPIはusだった。キャッシュにない公開データと個人別レビューを取得する際に、地域をまたぐ通信が発生していた。

## 変更

- 公開授業情報とセッションを並行して取得する。
- 公開の授業カードと投稿へのリンクを先に返す。レビューの取得を待つ間は、本文の代わりに読み込み中の表示を出す。
- レビューはサーバーで取得し、準備ができたらSuspenseの境界内を既存の画面へ切り替える。初期データの利用者キーとアカウント変更時の再取得を維持する。
- 読み込み中の授業カードは公開データだけを使う。ブックマークの操作は無効にし、レビューのための高さを確保して画面の移動を抑える。
- 単一の実行地域をiad1へ変更し、APIに近づける。拠点の追加・有料機能・メモリ増設は行わない。静的ファイルは引き続きVercelのCDNから配信される。

公開データの300秒キャッシュ、レビューのno-store、最終的なaccess_grantedの判定は従来どおり。認証情報を公開カードへ渡さず、レビューの取得に失敗した場合の案内も維持する。授業が存在しない場合は、レビューの取得を始めずに404を返す。

読み込み中の平均評価・件数には既存の公開キャッシュを使い、レビュー取得後は従来どおり最新の取得結果を表示する。先行表示用のHTMLが増えるため、表示開始の短縮とHTML転送量の両方を比較する。

## 回帰試験

`npm run verify` と `npm run e2e` に加え、本番ビルド後に以下を実行する。

```bash
npm run test:public-cache
npm run test:lecture-streaming
npm run e2e:security
```

`test:lecture-streaming` は実際のNext本番サーバーを起動し、公開APIの遅延を120ms、レビューを900msに固定して、レビューが返る前に授業カードが届くことを検証する。キャッシュの再利用、レビューの毎回取得、クローラー向けのメタデータと本文、レビュー取得失敗時の案内、404も確認する。画面試験でもレビューを3秒遅らせて先行表示を確認する。

本番では通常のChromeで、1440pxと390pxのそれぞれ1回の準備後に5回測定する。変更前後で同じURL・ブラウザ・キャッシュ条件を使い、中央値を比較する。FCP、LCP、授業情報とレビューの表示、HTMLの完了と圧縮後の転送量を記録する。単一の端末での測定であり、実利用者全体の統計ではない。

## 反映後の確認と切り戻し

主要画面・未ログイン時の保護・OGP画像を確認する。デプロイの地域とコミットを照合し、表示速度を再測定する。認証セッションを読むAPIも実行地域が変わるため、ログイン画面とセッションAPIも確認する。

問題があれば、変更前のVercelデプロイへ戻す。DBや環境変数の移行はない。
