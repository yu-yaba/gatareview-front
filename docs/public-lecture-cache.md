# 公開授業情報の共通キャッシュ

授業詳細の画面、メタデータ、OGP画像は `serverLectureApi.ts` の同じ公開情報取得関数を使う。授業ごとに1つの `unstable_cache` の項目（300秒で更新）を共有する。Reactの `cache()` は、同じサーバーレンダリング内で解析済みの結果も共有する。

`fetch` のData Cacheはリクエストヘッダーをキーに含めるため、利用者ごとに変わる署名付きIP（[API呼び出しの回数制限](#api呼び出しの回数制限と利用者ip)）を付けるとキャッシュが共有されなくなる。そこで取得自体は `cache: 'no-store'` で行い、`unstable_cache` のキーは授業のパスと接続先だけにする。署名はキーではなく関数の中で付けるので、キャッシュがない時の取得はその原因となった利用者の枠で数えられ、結果は全員で共有する。OGP画像のルートも要求ごとに実行される（画像自体はCDNが長期キャッシュする）ため、同じく要求者の署名を付ける。APIが200でも授業の形をしていない応答（`null` など）は保存せず例外にする。

この関数にはセッションやAuthorizationを渡さない。利用者ごとに閲覧可否が変わるレビューは、別の `getLectureReviewsForPage` が `cache: 'no-store'` で毎回取得する。動的なHTMLや個人別レビューをCDNやサービスワーカーに保存する変更ではない。

取得先や公開情報の更新間隔は従来どおり。更新期限後はNext.jsが古い値を返しながら再取得するため、更新から厳密に300秒以内の反映は保証しない。再取得に失敗した場合は最後の成功した値を保持し、次の要求で再試行する。

## 失敗時の表示

- APIが本当に404を返した授業だけを「ページが見つかりません」（404、noindex）にする。
- 429（回数制限）、5xx、JSONとして読めない応答、授業の形をしていない応答、8秒のタイムアウト、APIに接続できない場合は例外にし、`error.tsx` のエラー画面を5xxで返す。404として検索エンジンに伝わったり、キャッシュに保存されたりしない。次の要求で再取得する。タイムアウトした場合は別の接続先を試さない。
- 429による失敗は誰でも意図的に起こせ、Sentryの無料枠を使い切られるおそれがあるため送らない。例外に固定のdigest `API_RATE_LIMITED` を付け、Next.jsがサーバーとブラウザで報告するすべての写しを `monitoring.ts` の `beforeSend` で捨てる。エラー画面にはこの値がエラーIDとして表示される。5xx・タイムアウト・接続不可は従来どおり送る。
- レビュー一覧は授業カードを表示した後に読み込むため、失敗しても従来どおりページ内の再試行案内を出す。
- ホームの各欄は従来どおり、取得に失敗した欄だけに案内を出す。

## API呼び出しの回数制限と利用者IP

backendはIPごとに回数を制限するが、Vercelのサーバーからの呼び出しはHerokuからは全員が同じ送信元に見える。そのため授業詳細（公開情報のキャッシュがない時の取得とレビュー）、授業検索、Googleログイン、ログアウト時のAPI失効では、`backendRequest.ts` がVercelのエッジの設定する `x-real-ip` を読み、`RATE_LIMIT_FORWARDING_SECRET` によるHMAC署名と時刻を付けて送る（形式は `clientIpSignature.ts`、backendの `config/initializers/rack_attack.rb` と同じテスト値で固定）。

- 署名ヘッダーを付けるのは、鍵が32バイト以上あり、Vercel上（`VERCEL=1` かつ `VERCEL_ENV` が `development` でない）で動いている時だけ。`next dev`、Docker、Vercel外では利用者が `x-real-ip` を自由に送れるため付けない。
- `www.gatareview.com` はCloudflareのプロキシを通るため、通常の訪問では `x-real-ip` がCloudflareの中継サーバーのIPになり、多くの利用者が同じ枠を共有してしまう。Cloudflareは利用者のIPを `CF-Connecting-IP` に入れるが、Vercelへ直接接続すれば誰でもこのヘッダーを送れる。送信元がCloudflareのIPであることも証明にならない（他人のCloudflare Workerからも接続できる）。そこで、gatareview.comのゾーンのTransform Ruleが付ける秘密のヘッダー `X-Gatareview-Proxy-Secret` がVercelの `CLOUDFLARE_PROXY_SECRET` と一致した要求だけ `CF-Connecting-IP` を使い、それ以外は `x-real-ip` を使う（[設定手順](deploy-checklist.md#api回数制限の利用者ip転送)）。
- `x-forwarded-for` や利用者が送った `X-Gatareview-Client-Ip`、秘密のヘッダーのない `CF-Connecting-IP` は使わない。
- 署名はクエリと本文を含まない。漏れた署名は60秒間、同じメソッドとパスで別のクエリや本文に使い回せるが、数えられるのは署名されたIPの枠。署名はVercelとHerokuの間のTLS通信の中にだけあり、両方のSentryはリクエストヘッダーを送らない。
- backendが署名を無視した場合（鍵の未設定・不一致）でも、従来どおりの制限で動く。

## 検証

`npm run build` のあとに `npm run test:public-cache` を実行する。実際のNext.js本番サーバーと隔離したAPIで、画面とメタデータの取得共有、再訪時のキャッシュ、授業IDの分離、一時障害からの回復、レビューの毎回取得とログイン前後の分離を検証する。さらに、Vercelと同じ環境変数と `x-real-ip` を与え、APIへの呼び出しが利用者IPの正しい署名を持つこと、Cloudflareの秘密のヘッダーがある時だけ `CF-Connecting-IP` を使い偽の `CF-Connecting-IP` は無視すること、本当の404だけが404になること、429・500・503・不正なJSON・授業の形でない応答・タイムアウトが5xxのエラー画面になりキャッシュされないこと、OGP画像も要求者の署名を付け失敗時に404にならないことも検証する。タイムアウトの確認で約9秒かかる。CIでも実行する。

キャッシュの方針を変更するときは `CACHE_TEST_EXPIRY=1 npm run test:public-cache` で実際に5分待ち、期限後の更新と再取得失敗からの回復も確認する。

Issue: https://github.com/yu-yaba/gatareview-back/issues/55

## 変更前後の比較

同じNext.js 15.5.28の本番ビルド、同じローカルAPIとJSON、空の授業キャッシュで比較した。画面とメタデータの両方に同じ授業情報が表示されることも確認した。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 初回の公開情報取得数 | 2回 | 1回 |
| 公開情報のJSON転送量 | 280 bytes | 140 bytes |
| 2回目以降の公開情報の取得数 | 0回 | 0回 |
| 初回ページ取得時間 | 298.58 ms | 187.48 ms |
| 再訪5回のページ取得時間の中央値 | 10.82 ms | 9.14 ms |

転送量は公開情報のJSON本文だけを数えた。ヘッダー、HTML、レビュー、OGP画像やTLSは含めていない。ローカルAPIの公開情報取得に同じ30msの待ち時間を設けた。初回の時間は各1回の測定であり、ネットワーク全体や本番の表示速度の改善率を示す値ではない。レビューは、同じ6回の画面取得で変更前後とも6回取得され、個人別の情報をキャッシュしていない。
